# IS

**この目的は 2 つの半分から成り、後の半分が前の半分を裁く。**「どちらでも行える」が要求であり、「優先は WSL」は**両立が高くついたときに何を捨てるかを決める規則**である。∴ 本 node が持つ手段は「両方で同じように動かす」ことではなく —— ⑴ **platform に依る差を、名指した 1 箇所へ集める** ⑵ **集めきれない差は、黙らせずに述べる** ⑶ **捨てるときは Windows 側を捨て、捨てたと書く**、である。

⚠ **この目的が難しいのは code ではない。失敗が非対称で、しかも沈黙だからである。** CI は ubuntu 1 本しか走っていない ∴ **win32 でだけ壊れるものは機械に 1 度も映らない。** 実測 2026-09-10（この機体: win32、repo が `D:`・home が `C:`、node v24.18.1）—— `node --test` は ✖10、`scripts/consumer-check.mjs` は NG 4 で、**同じ commit の CI は緑だった**（`gh run list`、main 最新 ci は success）。

🔴 **そしてこれは新しい形ではない。木は既に同じ形を 2 度記録している** ∴ **3 度目である**（[[purpose-drift]]、2026-09-03 と 09-04）—— あちらの言葉では「**CI が緑**」は「*その platform で*通った」でしかない。

## 既に散らばっている観測

⚠ **本 node は、これらを他 node から引き剥がさない** —— どの `[done]` も、その node の手段が実現した事実である。**ここが足すのは「同じ軸の出来事だった」という 1 本の線だけである。**

| 何が起きたか | どこに在るか | 何が沈黙していたか |
| :-- | :-- | :-- |
| `boot-ritual` の CLI 検査が先頭 `/` を要求し、**POSIX でしか真になりえなかった** | [[purpose-drift]]（実測 2026-09-03） | win32 で常時赤・CI は ubuntu ゆえ緑 |

## 🔴 法は既に在った。2 つ目の実装が、それを通らなかった

⚠ **2026-09-04 の時点で、[[purpose-drift]] は答えを法として置いていた** —— 「**配布されるのは git が記録した mode である** ∴ **index は両 platform で同じ答えを持つ唯一の場所**」。純関数 `isExecMode` にしてあり、その doc は理由まで書いている:

> ⚠ **純関数にしてあるのは、どちらの platform からも両方の分岐を検査できるようにするためである** —— **片方でしか踏めない分岐は、直したそばから同じ穴を隣に空ける。**

🔴 **その隣の穴が、実際に空いていた。** `scripts/consumer-check.mjs` は同じ判定を **working tree の `stat()` で**行っており、win32 で偽陽性を出し続けていた（実測 2026-09-10 —— `bearing-ci.mjs` は index で `100755` なのに NG）。⚠ **法が無かったのではない。法が在り、2 つ目の実装がそれを通らなかった。**

⚠ **∴ 本 node が読む手段の中心はここに在る**: platform の差は「気をつける」で閉じない —— **判定が 1 箇所に無ければ、法は 2 つ目の呼び出し元で黙って破れる。**

## 優先が WSL であることの、今の意味

⚠ **現在この repo の開発は Windows 側で行われている**（実測 2026-09-10: `process.platform === 'win32'`、cwd は `D:\trust_project\bearing`、home は `C:\Users\umu_s`）。∴ **pin された優先順位と、実際に開発が起きている場所は、今は一致していない。**

⚠ **一致させる act は人間のものである** —— `# ESCALATION` を見よ。**本 node はそれを待つ間も「どちらでも行える」側を進められる** ∴ 手段は優先順位の確定に依存しない。

# ESCALATION

- 🔴 **この機体に WSL のディストリビューションが 1 つも入っていない**（実測 2026-09-10 —— `wsl.exe -l -v` が「インストールされているディストリビューションはありません」と応答し、`wsl.exe --install <Distro>` を促した）。⚠ **∴「優先は WSL」は、今この機体では実行できない状態にある。** 入れるか・どちらに checkout を置くか・repo を `D:` から動かすかは、**いずれも人間の act** である。⚠ **私はこの 1 台しか見ていない** —— 他の機体については何も述べていない。

# PROCESS

- [done] **checkout の改行を LF に固定した。** `.gitattributes` に `* text=auto eol=lf`（人間の決定 2026-09-10、WSL 標準へ寄せる）。⚠ **git の中は既に完全に LF だった**（実測 2026-09-10、tracked 112 file の**全数**を `git show :<path>` で検め、CRLF を含むもの 0 件）∴ 直すべきは checkout の側だけだった。⚠ **`core.autocrlf` より強く、しかも tracked である** —— machine-local な `core.autocrlf=false` では、効いている記録がどこにも残らず**次の機体で黙って再発する**。⚠ **旧い `.gitattributes` が閉じていたのは `*.sh` と `.githooks/**` だけで、あれらが塞いでいたのは「起動しない」という*目に見える*壊れ方だった** —— 黙って赤くなるほうは開いたままだった。**効果: `node --test` が ✖10 → ✔484/✖0。** ⚠ **再測は `node --test test/claude/bearing/*.test.mjs`**
- [done] **出荷物の mode を index に訊く形にした。** `scripts/consumer-check.mjs` の `buildShipped` が `git ls-files -s` から `modes` を組んで持ち回る。⚠ **写した側を測り直す道は塞がっている** —— `fs.chmod` 自体が win32 では exec bit に効かない（実測 2026-09-10: `chmod(0o755)` の後も mode は `666`）。**`modes` が引けなければ検査は落ちる側に倒れる** ∴ 取り違えが緑に化ける向きは無い。✅ **変異試験を当てた** —— `git update-index --chmod=-x` で index を `100644` に落とすと NG になり mode を名指し、`--chmod=+x` で戻して 28/28。⚠ **再測は `node scripts/consumer-check.mjs`**
- [todo] **exec bit の判定を 1 箇所へ寄せる。** 🔴 **`isExecMode` は `test/claude/bearing/bin-namespace.test.mjs` から export されており、`scripts/consumer-check.mjs` はそれを通らずに同じ判定を書いている** —— 上段の「2 つ目の実装が法を通らなかった」を、記録ではなく構造として閉じる。⚠ **完了は字面で確かめられる**: 判定の実装が 1 つだけになり、`node --test` と `consumer-check` が緑で、**exec bit を落とす変異が両方から赤くなる。**
- [todo] **CI が win32 でも同じ 3 門を走らせるようにする。** ⚠ **今 CI は ubuntu 1 本であり、この node が数えた 7 件のうち 5 件は「CI では映らなかった」が原因の一部である。** ⚠ **完了は「緑になること」ではない** —— 片方でだけ落ちたときに**それが分かる形になること**である ∴ run が両 leg を報告していれば倒せる。⚠ **落ちた側をどうするか（直すか、Windows 側を捨てると書くか）は、落ちてから判断する。**
- [todo] **platform に依って分岐する箇所を、機械が列挙できるようにする。** ⚠ **今それを知る手段は grep しかなく、増えたことに気づく機構は無い** —— `lib/shell.mjs` の外に散った分岐は、次に増えたとき誰も述べない（`carrier_allowed` が配る境界について解いたのと同じ形の穴である）。**完了は字面で確かめられる**: 既知の分岐を全て挙げること（陽性対照）と、報告が CI の出力に出ること。

# OBSERVATION

- **WSL 側の checkout で、3 門（`node --test` / `carrier-check.sh` / `consumer-check.mjs`）が緑になるか。** ⚠ **私はこの機体の win32 側からしか測っていない** —— そして上の `# ESCALATION` のとおり、**この機体には WSL のディストリビューションが無い** ∴ **今は誰も測れない。**
- **実際に WSL と Windows を行き来して開発したとき、片方でしか起きない摩擦が残っているか。** ⚠ **これは門では出ない** —— 門が見るのは我々の code の振る舞いであり、**path の打ちにくさ・editor の挙動・起動の速さは、使った人間にしか見えない。**
- **LF への固定が、他の機体で pull されたときに何を起こすか。** ⚠ **git の中身は動いていない ∴ diff は出ないはずだが、これは docs の読みであって実測ではない**（この機体でしか確かめていない）。
- **「優先は WSL」が、どこまでの費用を許すか。** ⚠ **本 node は「捨てるときは Windows 側を捨てる」と読んだが、*どこで捨て始めるか*は書けない** —— 例えば CI の win32 leg が赤くなったとき、直すのと「Windows では通らないと書く」のどちらを選ぶかは、その都度の判断である。

# DAG

- 関連: [[purpose-drift]] —— 🔴 **本 node の観測の半分はあちらに在る。** ⚠ **だが軸が違う**: あちらの手段は「**構造的に映らない drift** を安く機械的に可視化し、判定はしない」であり、platform はそこで見つかった**軸の 1 つ**である。本 node は platform そのものを目的に持ち、**どちらでも動くこと**と**優先順位**を扱う ∴ あちらの 3 層にも 2 種のズレにも触れない。⚠ **あちらが 2026-09-04 に置いた法（index が両 platform で同じ答えを持つ唯一の場所）は、本 node が借りる側である** —— 書き換えは要求しない
