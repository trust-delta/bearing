# IS

**圧縮との差は「選んだかどうか」である。** ネイティブ圧縮は反応的で不可視であり、落ちたものを誰も選んでいない。⚠ **本 node の価値は baton の構造ではなく authoring の judgment にある** —— 何を残し何を「git と目的から再導出できる」として捨てるか、その判断こそ圧縮に欠けているものだ ∴ **機械が触ってよいのは判断でない部分だけ**（退避・刻印・機械的な差分）で、取捨には一切触れない。

⚠ **2026-09-06、取捨の判断が 1 つ確定した —— merge 済みの決定は baton に載せない**（人間の決定）。baton は「**覆せる設計点 10 個**」という数を、PR #37 / #38 / #39 の本文を指す**裸の参照**として世代を跨いで運び、しかも `escalation: 0` が判断待ちを代表していないことの論拠に使っていた。⚠ **人間の逐語:「確かに覆せるかもしれませんが、現状の機構の実際の動作に不満が出たときに見直すべきであり、PR が merge された時点から今までにおいて問題が出ていないなら、その妥当性を検証すべき時ではない」** ∴ **あれは判断待ちではなく済んだ決定であり、見直しの発火点は時間ではなく不満である。**

🔴 **そして落とす直前に中身を開いたら、数の意味が違っていた**（実測 2026-09-06、対象: この repo の GitHub PR 全 39 本）—— 節を持つ PR は **8 本**、列挙された点は **25**、うち #33 は CLOSED で #34 がその再提出ゆえ 3 点は重複 ∴ **実質 22**。しかも後の PR が前の点を畳んでいた（#37「設計点 #30 のうち 1 つを覆し、1 つを保った」・#38「設計点 #35 は、点そのものが消える形で解決した」）。⚠ **∴ あの「10」は在庫ではなく直近 3 本の切片であり、在庫の顔で運ばれていた。** ⚠ **`設計点` は tracked な repo に 1 件も無い**（陽性対照つき: 同じ `git grep` で `覆せる` は `bearing.md` に 1 件拾う）∴ **機構は原理的に数えられず、点が退役したことも後の PR 本文の 1 文にしか残らない。** ⚠ **測る網も 1 度狭すぎた** —— `^#{1,4}\s*覆せる設計点` は PR #30 の `## 設計点 —— 覆せるもの` に一致せず**黙って 1 本落とした**（広い `grep '設計点'` で拾い直した）。**再測は `gh pr view <n> --json body` を全 PR に打つだけである。**

🔴 **∴ この node の取捨に効く形はこうである: baton は数だけを運んではならない。** ⚠ **参照は運べても、参照が支えているはずの主張は運べない** —— 数は世代を跨ぐたびに安く写せるのに、**それが何の在庫なのかは誰も再検算しない。** ⚠ **載せるなら、その場で主張ごと畳んで書く。畳めないなら、それは baton ではなく corpus に属する。**

**発火点は圧縮の直前である。** ⚠ **hook から使用率メーターを見る術は無い**（どの hook event の入力にも context の欄が無い）が、ハーネスは圧縮を決めた瞬間にそれを告げる。⚠ **これは閾値の代用ではなく閾値そのもの**で、しかも [[bearing]] の言う「置き換えない」に適う —— 圧縮を禁じるのではなく、**沈黙の破棄を 1 度だけ差し止めて選択を人へ返す**。

⚠ **baton が痕跡を残さないことは、この node の外にも効いている** —— [[adoption-declaration]] は「痕跡を残さない機能は user 単位で有効になる」の側に handoff を置く。⚠ **2026-09-03、その要求に合わせて置き場を repo の外へ出した**（人間が決定）: `~/.bearing/units/<unit>/`。以前は cwd の傍らの `.handoff/` に置き、「どの repo にも属さないので commit されえない」と述べていたが、⚠ **それが真だったのは multi-repo wrapper が cwd のときだけである** —— 単一 repo で使えば repo の中に生まれ、**ignore しているのは bearing 自身の `.gitignore` だけだった。** home の下へ出せば、commit されえないことが**どの使い方でも**構造として保たれる。

⚠ **越境しない不変は 1 文字も動いていない。** 動いたのは*どこに置くか*であって*誰の間に立つか*ではない —— machine-local は今も目的の帰結である。⚠ **引くのは unit root の path であって repo 名ではない**: 名前だけで引けば、同名 repo や複数 worktree が黙って同じ baton を共有する ∴ **別の対話の baton を読む**ことになり、それは baton が無いことより悪い。⚠ **置き場は `handoff/` の下に入れ子にした**（人間が 2026-09-03 に決定）—— `~/.bearing/units/<unit>/handoff/`。**baton はこの unit の持ち物の 1 つでしかない** ∴ 次に増えるものが baton の隣へ雑に積まれない。⚠ **平坦化の規則は Claude Code の `~/.claude/projects/` と同じにした**（人間が決定）—— **理由は一意性ではなく馴染みである**: 人間が自力で archive を見に行くときに読める。∴ **単射ではないことを承知で採っており、衝突は名前ではなく検出で塞ぐ。**

⚠ **数字が見えても発火点は動かない。** [[ambient-display]] は statusline の側から `context_window.used_percentage` を受け取れる —— **hook に無いものが、あちらには在る**。だがそれは人間が読む数字であって機構の起点ではない: statusline は hook ではなく、何も起動できない。∴ あの面が増やすのは**人間が自ら handoff を選ぶ機会**であり、この node の閾値を置き換えはしない。

⚠ **home の下へ出したことで、置き場は device を跨ぎうるようになった。** 2026-09-04、repo が `D:`・home が `C:` の Windows 機で `migrate` が `EXDEV` で落ちた —— **`rename` は device を跨げない**（実測）。⚠ **これは移行の事故ではなく通常形の 1 つである** —— **unit root は人間が選ぶ場所に在り、home は選べない** ∴ 別 drive に repo を置く形はありふれており、跨ぐことは例外ではない。⚠ **落ちたのが 1 本目ゆえ何も移らずに止まったが、それは幸運であって設計ではない** —— 2 本目で落ちれば baton は半分だけ移った状態になり、**旧い置き場と新しい置き場に別々の baton が並ぶ**（機構は前者をもう読まない）。

⚠ **人が自ら圧縮を指示したときは決して差し止めない。** 人の act を、その人のための儀式で上書きするのは体制の反転である。

⚠ **この node は aim から独立していなければならない**（人間が 2026-09-04 に明示）—— **handoff は `/bearing:with-aim` 無しで動かねばならず、aim の側も handoff の機構を必要としない。** [[adoption-declaration]] が既にそれを法として持っている（baton の未読は、採っていない project でも述べる唯一の例外である）。

⚠ **だが実装は 2 箇所でその分離を破っていた**（2026-09-04、人間が指摘し、実測で確かめた）。⑴ **hook が repo の中の path を正本として名指していた** —— `bin/boot-ritual.mjs` は **aim の gate を持たず**、baton が未読ならどの repo でも発火するのに、`docs/aims/_guide/handoff.md` を正本と述べていた。⚠ **corpus も `CLAUDE.md` も無い repo に baton だけ置いて走らせると、実際にそう述べた** —— そこには何も無い。⑵ **`/bearing:with-aim` が `handoff.md` を消費する repo の `_guide/` へ置いていた** ∴ **handoff の canon が aim の採用に依存する**形になっていた。

⚠ **どちらも「skill が全部を運んでいる」ことを見落としたために起きた。** `handoff-r` / `handoff-w` の carrier は自分の同梱物を**裸の名**で指しており、**repo 側の `_guide/handoff.md` を 1 度も要求しない**（実測 2026-09-04）∴ 正しい名指し先は最初から skill の同梱物だった。

⚠ **2026-09-05、`_guide/handoff.md` の置き場という問いは消滅した**（人間の決定）—— **`docs/aims/_guide/` そのものが廃されるからである。** 配布する md の正本は単位ごとに分かれ、handoff は自分の dir を持つ。∴ **handoff の正本は `skills/handoff/` に住み、aim の dir に間借りしない**（⚠ **2026-09-05 に一度 `original/handoff/` を経由した** —— 同日 `original/` が畳まれ、carrier が正本になった。**分離は置き場が動いても保たれている**） —— ⚠ **上段が述べてきた分離が、説明ではなく配置で保たれる形になった。**

**そして skill は 2 枚から 1 枚になる。** `/bearing:handoff r` / `w` の引数で分岐し、共通事項を `skill.md` に置き、`read.md` / `write.md` を追加で読む。⚠ **分岐はハーネスではなくエージェントが行う** —— 今の `handoff-r` が既にその形で動いている（実測 2026-09-05: SKILL.md が「同梱の `handoff.md` の § 読む を読め」と述べ、エージェントがそれを読んで実行した）∴ **新しい機構は要らない。** ⚠ **`$ARGUMENTS` は `skills/` でも展開された**（実測 2026-09-05、Claude Code、cache `0.17.0` から `/bearing:handoff r` を打った初回 —— 同梱の SKILL.md の字面は `$ARGUMENTS` だが、harness が渡した本文では `r` に置き換わっていた）。⚠ **それでも「展開されなくても壊れない形」は落とさない** —— **これは他人の系の振る舞いであり、向こうが変えた瞬間に黙って偽になる。** SKILL.md は今も「どちらで呼ばれたかを見よ。判別できなければ問え」と述べており、⚠ **失敗は沈黙ではなく質問として出る。** 再測は `/bearing:handoff r` を 1 度打ち、渡された本文に `$ARGUMENTS` の字が残っているかを見ること。

⚠ **2 枚が同じ 110 行を運んでいたのは、内容が 1 つの儀式だからである。** `## 置き場` は両方が要り、**読む側は書く側の原則を要る** —— 手順 4 の trace は「baton は forward に選ぶ」から導かれた対処であり、**過少報告することを知らなければ、ただの儀式に見える。** ⚠ **∴ 答えは分割ではなく 1 skill 化である** —— 割れば共有部分が 2 正本になり、この repo が一貫して拒んできた形になる。

⚠ **2026-09-07、入口だけが 2 つに戻った —— canon は 1 つのままである。** 🔴 **引数つきの形は、サジェストから選んでもそのままでは打てない**（人間の指摘 2026-09-07、CLI とデスクトップの両方）—— 選んだ後に `r` / `w` を人間が手で足すことになる。⚠ **引数なしで打てば skill は問い返す** ∴ 壊れてはいない —— **増えるのは往復であって、誤りではない。** ∴ `commands/handoff-r.md` / `handoff-w.md` を置いた。🔴 **上段が拒んだのは「canon を 2 つ持つこと」であって「入口が 2 つ在ること」ではない** —— 旧 `handoff-r` / `handoff-w` は**各々が 110 行の複製を抱えていた** ∴ **中身を持たない別名は、あの理由に触れない。** ⚠ **別名は path ではなく skill を名指す** —— `${CLAUDE_PLUGIN_ROOT}` が command 本文でも展開されることはこの repo が 2026-09-03 に実測しているが、**今回はその展開に依っていない** ∴ 他人の系がそこを変えても、別名は壊れない。

⚠ **2026-09-07、その別名が面に出ることも確認された** —— **新しいプロセスでサジェストに 3 項（`handoff` / `-r` / `-w`）が並んだ**（人間の観測 2026-09-07、1 機体・1 セッション）。⚠ **PR #50 はこれを 1 度も見ていない** —— 走っているセッションは版を掴んだまま動かないからである（[[bearing]] の 4 時定数）∴ **試験の緑と、面にそう出ることは、別の瞬間にしか確かめられなかった。**

🔴 **そして人間は、これを効率の話ではないと述べた**（人間の指摘 2026-09-07）。⚠ **以下はその指摘に対する私の読みであって、人間が述べた言葉ではない。** —— この方式の価値は **authoring の judgment** に在り、native な圧縮との違いは**極性**である（あちらは天井に当たってから発火する reactive、こちらは区切りの良いところで早めに選ぶ proactive）。⚠ **judgment の質は、選ぶ時点の context の質に依る** ∴ **劣化してから呼べば、劣化した材料の上で何を残すかを選ぶことになり、handoff は native な圧縮の劣化版に落ちる。**

🔴 **∴ 入口の摩擦は、handoff を reactive の側へ押し戻す力である。** ⚠ **呼ぶのが高ければ人間は先送りし、先送りするのは「まだ大丈夫」と感じている間だけである** —— **その感覚が既に外れていることを教えるものは、この機構に無い**（statusline の使用率は人間が読む数字であって、何も起動しない —— 上段）。∴ **安さは効率ではなく、handoff が handoff であるための条件である。**

⚠ **もう 1 つ、安さはセッションを畳む決断そのものを安くする。** 畳んで開き直すのが高ければ、人間は劣化したセッションに留まる —— ⚠ **そして [[bearing]] が測ったとおり、slash command の一覧と Bash の PATH は新しいプロセスでしか追随しない** ∴ **留まることは、この plugin 自身の更新が届かないことでもある。** 🔴 **これは handoff の外にある帰結である** —— **安い handoff は、機構全体の追随の前提条件になっている。**

⚠ **2026-09-08、人間は上の読みを是としたうえで、狭いと述べた**（人間の指摘 2026-09-08）—— 🔴 **「handoff が安いこと ＝ 新鮮な context の session に相対的に長く居るということ。それは経験上も仕組み上もエージェントの出力の質を上げる」。**

⚠ **上の読みは baton を*書く瞬間*の judgment だけを見ていた。** 人間が見ているのは**滞在時間の配分**である —— 安ければセッションは短く区切られ、**劣化した context で働く時間の割合そのものが下がる。** 🔴 **∴ 安い handoff が上げるのは「引き継ぎの質」ではなく、「引き継ぎと引き継ぎの間に行う仕事すべての質」である。**

⚠ **根拠は 2 つあり、確信の階級が違う。** ⑴ **経験上** —— **人間の経験であって、この repo の実測ではない**（人間がそう述べた 2026-09-08）。⑵ **仕組み上** —— 新しいプロセスは法の block・aim facts・baton を**劣化前の形で丸ごと**受け取り、⚠ **さらに [[bearing]] が測った 4 時定数のうち 2 つ（slash command の一覧・Bash の PATH）は新しいプロセスでしか追随しない** ∴ **長く居るセッションほど、古い版の道具で働いていることになる。**

⚠ **∴ 上段の「安さは handoff が handoff であるための条件である」は今も真だが半分である** —— **残り半分は、安さが handoff の*外側*の時間に効くことである。**

⚠ **2026-09-08、人間が `aim:` の意図そのものを述べた**（人間の説明 2026-09-08）—— 🔴 **上の 2 つの読み（極性・滞在時間）はどちらも*安さ*の話であり、そもそも*なぜ native な圧縮ではないのか*を 1 つも述べていなかった。** 理由は 3 つ在る:

⑴ 🔴 **目的が違う ∴ 選ぶ基準が違う。** ⚠ **native な圧縮は「要約」と名乗る。だが「その会話のまとめ」と「次のセッションへ運ぶ情報」は別物である** —— **あちらは*そのセッションを続けるため*に畳むのであって、*新しいセッションへ運ぶため*ではない。** ⚠ **上段が「極性が逆」と述べたのは*いつ*発火するかの話だが、これは*何を選ぶか*の話であり、別の軸である。** 🔴 **∴ 仮に native の圧縮が完璧に要約しても、それは handoff の代わりにならない** —— **良い要約と良い baton は、同じものの品質差ではない。**

⑵ ⚠ **機構が見えない。** **どんな指示で畳まれ、どのモデルが畳んでいるのかが、使う側に示されない** —— **「もしかしたら haiku かもしれない」**（人間の言葉 2026-09-08）。⚠ **これは推測であって観測ではない —— 我々は確かめていない。** 🔴 **そして「確かめていない」こと自体が論点である**: **使う瞬間に面が何も述べないなら、確かめるには外へ出るしかなく、外へ出て確かめたことは向こうが変えた瞬間に黙って偽になる**（`CLAUDE.md` の記録の作法）。

⑶ 🔴 **∴ 人間が求めたのは「見える指示で、会話と同じモデルが authoring すること」である**（人間の説明 2026-09-08）。⚠ **canon は読める md であり**（`SKILL.md` ＋ `read.md` / `write.md`）**、baton を書くのはその対話をしてきた当のエージェントである。** ∴ **上段の「価値は authoring の judgment に在る」は、この 2 つが揃って初めて意味を持つ** —— ⚠ **見えない指示で正体の分からないモデルが選んだものは、judgment ではなく単なる出力である。**

⚠ **∴ `aim:` は動かない。** 「ネイティブ圧縮に委ねず」が ⑴⑵ を、「何を残し何を捨てるかを選んで」が ⑶ を、既に 1 文で運んでいた —— 🔴 **欠けていたのは目的ではなく、この `# IS` が理由を持っていなかったことである。**

⚠ **同日、人間がもう 1 つ足せと述べた**（人間の決定 2026-09-08）—— 🔴 **baton の仕事は「全部を運ぶこと」ではなく「畳むことを安くすること」である。** ⚠ **全部を運ぼうとする baton は*書く費用*を上げ、それはそのまま*畳む費用*に化ける** ∴ 上段のとおり、**高い畳みは先送りされ、先送りは劣化した context での仕事に化ける。** 🔴 **∴「何を捨てるか」は惜しい損失ではなく、機構の本体である** —— `aim:` の「何を残し何を捨てるかを選んで」は、**捨てることを許容しているのではなく、要求している。**

⚠ **∴ baton の良さは、運んだ量では測れない。** 上の ⑴ の分岐がここに効く: **要約の目的関数では短さが善だが、baton では短さも長さも善ではない** —— 🔴 **善は「次が同じ道を歩き直さないこと」であり、それは長さと相関しない。**

⚠ **同日、人間が使い心地を述べた**（人間の観測 2026-09-08）—— **「今のところ handoff の動作や内容に不満は見つけられません」**、そして **「land 前に見れることが大きいのかも」**。⚠ **後者は人間が仮説として述べたものであって、断定ではない。**

🔴 **その仮説を上の ⑵⑶ の隣に置くと、可視性は 3 段に分かれる。** ⑵ は**指示が見える**こと、⑶ は**書き手が見える**こと —— **3 つ目は、成果物が*効き始める前に*見えることである。** ⚠ **baton は人間の home の下に置かれた md であり、次のセッションへ渡る前に人間が開いて読める** ∴ **中身に不満が在れば、渡る前に直せる。** 🔴 **native な圧縮にこの段は無い** —— **畳まれた時にはもう畳まれており、何が捨てられたかは見えない。** ⚠ **`SKILL.md` 冒頭の「何が失われたかが不可視になる」の、時間の側の形である。**
